[RC-A] ROOT CAUSE (confirmed) — MultiValueStats list()/values() panic
----------------------------------------------------------------
Reproduced: `source=<2-shard parquet idx> | stats list(integer_number) as int_list`
  → 500 "execute_local_plan: CPU spawn failed: Panic { index out of bounds: the len is 1 but the index is 1 }"

Exact panic location (from cluster stderr, RUST_BACKTRACE off):
  datafusion-common-53.1.0/src/dfschema.rs:371:31
  pub fn qualified_field(&self, i: usize) -> ... { (self.field_qualifiers[i]..., self.field(i)) }
  → field_qualifiers[1] on a schema with len 1.

Java call path (from stack trace):
  ReduceStageExecutionFactory.createExecution → DatafusionReduceSink.<init>
  → NativeBridge.executeLocalPlan  (the COORDINATOR REDUCE / FINAL merge stage)

Mechanism:
  - Only triggers with >=2 shards (single shard has no reduce/merge stage) and only for
    SCALAR (no group-by) list()/values(). Grouped list() fails differently (see RC-D:
    "Field reference offset (2) must be less than number of fields in struct (2)").
  - FINAL list/values is rewritten to LOCAL_LIST_MERGE_OP (PplAggregateCallRewriter:288-311).
    The Java rewriter args are bounds-correct.
  - The FINAL reduce fragment handed to executeLocalPlan references field index 1 (a
    group/qualifier column) when the reduce input schema has only 1 column (the single
    list state column, no group key). DataFusion's qualified_field(1) then panics.
  - i.e. the substrait/relabel for the no-group-by FINAL list-merge reduce emits a
    field reference (offset 1) that assumes a leading group column that isn't present.

Affected (16): all CalciteMultiValueStatsIT list*/values* WITHOUT group-by.
NOT a UDAF bug — list_merge.rs accumulator is bounds-safe (loops 0..len). The bad field
reference is built upstream when constructing the reduce/FINAL plan for the no-group case.

STATUS: root cause located (DataFusion qualified_field(1) on 1-col reduce schema).
Fix candidate: in the FINAL list-merge reduce-plan / substrait emit, do not emit a
group-column field reference (offset 1) when groupCount==0.

[RC-A] ROOT CAUSE PINNED (input + output dumps captured)
----------------------------------------------------------------
attachFragmentOnTop receives:  LogicalAggregate(group={}, LIST($0))
                                 <- LogicalProject(integer_number=$4)
                                 <- StageInputTableScan(input-0, 8 cols)

Inside convertStandalone(aggregate), PplAggregateCallRewriter.liftListValuesOperandsToVarchar
fires for LIST(scalar int): it inserts a "lifting Project" that PASSES THROUGH the input
columns then APPENDS a VARCHAR cast column, and rewires LIST to point at that appended column
(index = inputCols + castSlot). So the measure becomes array_agg(field = <lifted cast idx>).

Then rewire() REPLACES the aggregate's input with the externally-converted inner Project bytes
(the original 1-column integer_number projection) — DISCARDING the lifting Project. The measure's
rewired field reference (here field:1) now dangles over a 1-column input -> DataFusion
qualified_field(1) on len-1 schema -> PANIC.

Confirmed via stitched proto: read=8 cols, project output_mapping:8 -> 1 col (field 4),
aggregate measure arg = field:1 (the lifted cast slot), but project output has only field 0.

FIX DIRECTION: in attachFragmentOnTop / convertStandalone for an aggregate that lifts
List/Values operands, the lifting Project must be preserved in the stitched plan (rewire must
keep it between the aggregate and the replaced inner), OR the lift must be applied to the inner
Project bytes too. The measure field reference and the actual emitted input schema must agree.
Likely fix in DataFusionFragmentConvertor.rewire/attachFragmentOnTop or by having the lift run
on convertFragment(project) inner as well.
